# Findings 2026-11-21 (kernel 7.3.4 source trace)

All file:line citations are from the matching distro source tree
`/usr/src/linux-7.3.4-1/` (openSUSE kernel-source 7.3.4).

## Incident timeline (2026-11-21 morning), established from logs

- 00:24:56 kernel: `DMUB HPD IRQ callback: link_index=5` (monitor powered off)
- 00:24:57 kernel: `PM: suspend entry (s2idle)`; systemd-logind `Suspending...`
- The compositor log shows **no DP-4 disconnect and no DPMS events overnight** —
  the monitor-off HPD was never processed into a connector removal before suspend.
- 09:00:21 resume (`PM: suspend exit`); HPD IRQs follow; owner powers monitor on →
  fine vertical stripes. Three owner replug cycles (09:00:39–09:01:55, Thunderbolt
  dock flaps in kernel log) with compositor modesets do **not** cure.
- 09:09 global DPMS disable (4 s) → enable **cures** it. No reboot needed.
- While striped: DRM state normal; framebuffer screenshots clean; DPCD via
  `/dev/drm_dp_aux4`: `LINK_BW_SET=0x1e` (HBR3), 4 lanes, lane status `0x77/0x77`,
  DSC off; eDP always correct.

Typical nights differ: the system stays **awake all night** (workloads), only the
monitor is powered off; hypridle DPMS-offs outputs after 10 min. Owner reports the
same stripes those mornings. These are two trigger classes; whether they share one
root cause is the open question.

## What the source says (verified locally)

1. **Stream-enable failures are deliberately adopted as success.** In
   `display/dc/link/link_dpms.c`, SST DP training failures are converted to
   `DC_DPMS_SUCCESS` (lines 2504, 2655, 2669, 2682, 2783), `link_state_valid` is set
   before training, and `dce110_apply_single_controller_ctx_to_hw()` ignores
   `set_dpms_on()`'s result and returns `DC_OK`
   (`display/dc/hwss/dce110/dce110_hwseq.c:1819-1846`).
   → *Normal-looking DRM state is not proof that a stream was ever successfully
   established.* This alone does not explain persistence across replug cycles,
   but it means a failed first enable can leave software believing all is well.
2. **Normal resume rebuilds state** (`dm_resume()` → `dc_set_power_state(D0)` →
   `init_hw`, then `drm_atomic_helper_resume()` recommit of the cached config;
   `display/amdgpu_dm/amdgpu_dm.c:1504-2069`). HPD notifications are skipped while
   `in_suspend` (`amdgpu_dm_irq.c:1644-1648`). An absent SST sink can become a
   *virtual* sink during restore (`amdgpu_dm_connector.c:1033-1046, 1494-1504`) —
   so resume does not necessarily "train into thin air"; the actual sink/training
   result at restore is evidence we still need.
3. **DPIA pretraining is OFF for this ASIC.** `enable_dpia_pre_training` is only set
   for `DCE_HWIP >= 4.2.0` (`amdgpu_dm.c:605-611`), not DCN 3.5.1. Detection
   therefore skips destructive link-capability verification for USB4/DPIA endpoints
   (`display/dc/link/link_detection.c:966-971`), and `DC_SKIP_DETECTION_LT`
   (0x200000) is a no-op probe here.
4. Already-present fixes that do **not** need re-proposing: DCN35 periodic-detection
   restore (`display/dc/clk_mgr/dcn35/dcn35_clk_mgr.c:422`) and the
   partially-updated-pipe-context DPMS fix (`display/dc/core/dc.c:4464-4482`).

Related upstream context: the October 2026 amd-gfx report (155555) describes
cached-state resume + failed training ignored for DPIA/MST (drm/amd#6012) and
proposes pruning cached CRTCs of lost DPIA links; not merged, and its stale-MST
payload mechanism does not directly apply to this SST stream. No exact duplicate
of this bug was found upstream.

## Hypothesis ranking

1. **Failed/incomplete first stream enable adopted as success** (shared by resume
   restore and awake DPMS-on/hotplug), leaving hardware–software disagreement
   downstream (ODM pipes / clocks) that later modesets don't repair because
   software thinks nothing changed.
2. **Display idle-power (IPS/DMUB) exit mis-restoring state** on the awake class
   (testable with `amdgpu.dcdebugmask=0x800`, `DC_DISABLE_IPS`). IPS bits verified
   in `include/amd_shared.h:357-380` (`0x800` disable IPS, `0x4000` *force* IPS).
3. ODM-combine/MPC programming defect for the 5120-wide stream downstream of the
   above transitions.

## Armed for the next natural reproduction (2026-11-21 evening)

- `drm.debug=0x156` (runtime; resets on reboot) for enable-boundary logging.
- The guard daemon captures `tools/stripes-capture.sh auto-precycle` (DRM state,
  DPCD, kernel/compositor logs) **before** it DPMS-cycles DP-4.
- The guard's DP-4-only cycle is the first discriminator:
  - cures → per-stream state (hypothesis 1 as pure per-stream);
  - fails → next manual steps: eDP-only cycle with DP-4 active, then global cycle
    enabling DP-4 *before* eDP (separates zero-stream reset vs eDP reset vs order).

## Patch plan once discriminated

- If enable-failure adoption is confirmed: propagate `set_dpms_on`/SST training
  failure (or force full backend reprogram) instead of `DC_DPMS_SUCCESS`.
- If resume-only: prune cached CRTCs whose DPIA link is gone before restore.
- If IPS: fix is in DMUB/DCN3.5 idle-exit state restore; workaround param until then.
- Build/sign only the `amdgpu` module (`CONFIG_DRM_AMDGPU=m`), own MOK key for
  Secure Boot, prove over multiple overnight cycles, ship via `reapply.sh` here,
  submit to amd-gfx mailing list with the GitLab issue.
